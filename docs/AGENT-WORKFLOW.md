# AGENT-WORKFLOW — tickets, worktrees, PRs, roles

Long form of `AGENTS.md` §Work protocol. All commands below are the real, committed ones
(`tools/tickets.py`, `tools/wt.sh`, `tools/pr.sh`, `tools/check.sh`,
`tools/setup-review-remote.sh`, `tools/steward.sh`) — proven end to end on DS-000
(see `prs/DS-000.md`, `prs/DS-000.review.md`, `docs/workflow-smoke.md`).

## Roles

- **Steward** (`agents/deckstack-steward.md`, launched with `sh tools/steward.sh "<task>"`):
  triages the ready set, assigns/claims, checks file collisions, reviews PRs, runs
  acceptance, requests changes, merges, keeps the board truthful and main green, runs
  `recover`, escalates architecture conflicts to the owner. Only role that lands work on
  `main`. Never implements feature tickets. The steward runs with `DS_STEWARD=1` exported
  (`tools/steward.sh` does it): `tools/pr.sh review`/`merge` refuse to run without it and
  refuse self-approval (reviewer identity == ticket owner), so a worker can never approve
  or merge its own PR — hand the PR to the steward instead.
- **Worker** (coding agent): claims one ticket, works in one worktree, opens one PR.
  Never commits to `main`, never lands its own PR.

## Ticket states (tools/tickets.py)

```
backlog → ready → doing → review → done
   ↑        ↓        ↓        ↓
   └──── blocked ←─┴────────┘   (blocked always carries blocked_reason)
```

One ticket = one PR = one worktree. Tickets carry: id, title, state, phase, lane, size,
owner, depends_on, touches (the ownership list), branch/worktree/pr, acceptance,
verification. Only `depends_on` is authored by hand; `sync` computes `blocks`, the
graph, and auto-promotes backlog → ready when all deps are done.

## Setup (once per clone)

```sh
sh tools/setup-review-remote.sh     # git init --bare .review.git (ignored), remote `review`, push main — no network
sh tools/bootstrap.sh               # .venv + requirements + sh tools/check.sh
```

## Claim → worktree → commit → PR → review → land

```sh
# worker, from the MAIN worktree:
sh tools/wt.sh new DS-XXX --owner <name>
#   -> claims via tools/tickets.py (refuses dirty main / non-ready ticket / touch
#      collision), commits ONLY the ticket metadata to main as a coordination commit,
#      creates .worktrees/DS-XXX on branch ticket/DS-XXX from main, prints next commands
cd .worktrees/DS-XXX
# ... edit ONLY the paths in the ticket's touches ...
git add -A
git commit -m "ticket(DS-XXX): <subject>" -m "Generated by Mistral Vibe." \
  -m "Co-Authored-By: Mistral Vibe <vibe@mistral.ai>"
sh tools/pr.sh submit DS-XXX
#   -> MUST run inside .worktrees/DS-XXX on branch ticket/DS-XXX (pwd is verified against
#      the main repo's .worktrees/<id>); requires clean tree, >=1 commit ahead of main with
#      a ticket(DS-XXX): subject; runs tools/check.sh in that worktree; writes prs/DS-XXX.md
#      from prs/TEMPLATE.md (base/head, commits, diffstat, checks, risks); sets state
#      review; commits PR record + ticket metadata on the branch; pushes ticket/DS-XXX to
#      review

# steward, on main (steward-only: DS_STEWARD=1 is exported by tools/steward.sh; a manual
# steward shell uses `DS_STEWARD=1 sh tools/pr.sh …`):
sh tools/pr.sh list                                   # open PRs: ticket, owner, branch, verdict, ahead/behind (parsed from tickets.py list --json)
sh tools/pr.sh review DS-XXX --approve                # or --request-changes "reason"; no flag => changes-requested
#   -> refuses without DS_STEWARD=1, and refuses when the reviewer identity equals the
#      ticket owner (self-approval); workers must hand off to the steward
#   -> fetches review, shows the diff, runs tools/check.sh IN .worktrees/DS-XXX
#      (check.sh validates the tree it is given / invoked from), checks the diff against
#      the ticket touches with `python3 tools/tickets.py check-touches DS-XXX --diff main...ticket/DS-XXX`
#      (fnmatch globs + directory prefixes; refuses --approve on files outside touches),
#      writes prs/DS-XXX.review.md (verdict, checks, findings, reviewer),
#      commits it on main as a coordination commit
sh tools/pr.sh merge DS-XXX
#   -> steward-only (same DS_STEWARD=1 + no-self-merge gate); requires verdict approved;
#      rebases ticket/DS-XXX onto main in the worktree; on a rebase conflict it runs
#      tools/resolve-rebase.sh once, which auto-resolves the whitelisted generated/workflow
#      paths and continues the rebase (see "Conflict avoidance" below); a conflicting path
#      outside the whitelist stops the merge with a manual-resolution message, worktree
#      intact. It then re-runs tools/check.sh there,
#      lands on main --no-ff with a message naming ticket + PR, sets the ticket done on
#      main, commits the board, removes the worktree, deletes the branch locally and on
#      review, pushes main to review AND VERIFIES the remote sha (fails loudly if the
#      push did not land).

# inspection / recovery:
sh tools/wt.sh list                    # worktrees vs board in-flight
sh tools/wt.sh remove DS-XXX           # cleanup for done/abandoned tickets only
python3 tools/tickets.py ready         # ready set + next-up
python3 tools/tickets.py recover       # dangling doing/review tickets (branch/worktree/pr)
python3 tools/tickets.py validate      # board gate (also: generated files in sync)
python3 tools/tickets.py sync          # regenerate BOARD.md/GRAPH.md/index.json
python3 tools/tickets.py check-touches DS-XXX --diff main...ticket/DS-XXX   # diff within touches? (globs/dirs/new:)
python3 tools/tickets.py add-touch DS-XXX --add <path> [--add ...]   # extend touches when scope must change (lock + validate + sync; refuses duplicates, invalid entries, doing-ticket collisions)
python3 tools/tickets.py show DS-XXX --json   # full metadata, machine-readable
python3 tools/tickets.py field DS-XXX state   # one field
```

## Conflict avoidance

- `touches` is the ownership list; `tools/tickets.py claim` (and `wt.sh new`) refuse a
  claim that overlaps a doing ticket's `touches` (`validate` also reports it as a
  `file collision` error). If scope must change mid-flight, extend `touches` through the
  tool — `python3 tools/tickets.py add-touch DS-XXX --add <path>` — never by hand-editing
  the ticket's metadata block.
- Contracts (`schemas/`, `docs/contracts/`) are high-contention: one ticket at a time.
- `.worktrees/` and `.review.git/` are gitignored; `prs/<id>.md` records are committed.
- Rebase conflicts in `pr.sh merge` auto-resolve only for the generated/workflow paths
  whitelisted in `tools/resolve-rebase.sh`: `tickets/BOARD.md`, `tickets/GRAPH.md`,
  `tickets/index.json`, `tickets/DS-*.md` (taken from main with `checkout --ours`, then
  regenerated/normalized by the post-merge `tickets.py` calls) and `Cargo.lock` (taken
  from main, then regenerated with `cargo generate-lockfile --offline`).
  Every other conflicting path — source, contracts, docs, `prs/`, `docs/run-log.tsv` —
  stays manual: `tools/pr.sh merge` stops with the manual-resolution message and leaves
  the worktree intact for a human.

## Verification (every PR)

`sh tools/check.sh [tree-root]` — validates the tree it is invoked from, or the explicit
`tree-root` argument (`pr.sh review`/`merge` pass `.worktrees/DS-XXX`, so the worktree content
is what gets gated, not main). Always: `sh tests/fixtures/validate.sh` (ALL CHECKS PASSED) +
`python3 tools/tickets.py validate` (DAG + generated files in sync); conditional:
`cargo fmt --check` / `cargo clippy --workspace -- -D warnings` / `cargo test --workspace`
once `Cargo.toml` exists (DS-004), `tests/conformance/run.py` once it exists (DS-018).
Then ticket-specific acceptance, and a stale grep for the ticket's area. Hardware
tickets additionally: `DS_HARDWARE=1 python tests/hw/smoke.py` (DS-026) and, for pixel
claims, the camera harness (`docs/90-verification.md`, deckstack-verify).

## Escalation

Stop and escalate to the steward (then Autolith/owner) when: a ticket needs a contract
change another open ticket also touches; a test is flaky on real hardware (file it, don't
retry-loop); a scope rule in `docs/00-scope.md` seems wrong (propose an amendment to
BRIEF.md, don't silently relax); hardware behaves differently from ds-vdev (fix the
virtual model first); the workflow scripts themselves fail (fix under DS-002, don't work
around silently).

## CLI self-description contract (referenced by all steering docs)

Normative in `docs/contracts/cli.md` (lands with DS-016/DS-062): `ds --help` /
`ds <group> --help` / `ds <group> <verb> --help` always present; `ds schema <name>` prints
the JSON Schema from `schemas/`; `ds describe <path>` prints schema + current value +
allowed verbs; output is `--json` (one object) or `--ndjson` (streaming verbs only;
`--json` there is exit 1); exit codes 0–8 are stable and documented; errors are
actionable (`ds: path not found: … [exit 2]`). Agents must be able to discover every
capability from the CLI alone — no UI required (R1/R10).
