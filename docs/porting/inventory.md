# Porting inventory — old HubDeck/MasterHub behaviours (DS-071)

Scope delta 2 / delta 7 (`docs/00-scope.md`, `docs/70-porting-notes.md`): **reimplement, never
import.** No exporter/importer, no `ds migrate`, no compatibility layer, no code copied from
`hubdeck/` (Python) or `hubdeck-upstream/` (Rust). Every row below is a behaviour worth
considering, reimplemented by hand against `schemas/` + `docs/contracts/*`, one ticket at a
time. Old locations are cited as recorded in the read-only evidence base `docs/discovery/*`
(prefixes: `hubdeck/` = `the Python predecessor checkout`, `upstream/` =
`the Tauri predecessor checkout`); the `evidence` column names where the claim is
recorded and, for ported rows, what actually ran.

Status vocabulary: **ported** (landed and proven on ds-vdev), **not needed** (the new design
already covers it, or the brief rejects it), **post-alpha** (a real behaviour that needs a
core/contract change or its own ticket lane — the lane is named).

## Rules this inventory obeys

- No import/migration/compat layer is proposed anywhere above (scope delta 2, ADR-012): rows
  that would need one (11) are marked post-alpha with the lane named, not scheduled.
- Nothing with `{python: …}` code-in-config (row 4) is ported as code-in-config; it becomes
  an external script behind an `exec` binding or a plugin (R8).
- IDs (rooms, lights, keys) come from user/agent-created state (`/plugins/lights/config`,
  `/controls/…`), never scraped from the old config.
- The one worked example — row 2, the Salon key — is `docs/porting/salon-key.md`, a run that
  exits 0 on ds-vdev with the fake HueMux.
