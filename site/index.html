deckstack

One Rust daemon owns the MasterHub deck. Your deck logic is a client.

View source on GitHub How it is built How it compares Reference plugin

The MasterHub deck is a 15-key panel with a dial, two rollers and per-key RGB. The software we started from put device input and output, painting, plugins and a desktop UI in one process. deckstack splits that into a daemon that owns the device and a protocol that everything else speaks.

What runs

ds-daemon

Owns the HID device, the state document and its revision counter, the binding router, the frame writer and the plugin host. It is the only process that writes to the deck.

ds

A stateless CLI. Each call connects to the socket, sends one request, prints the result and exits. ds watch holds a subscription open.

ds-mcp

An MCP server over stdio. It exposes the same daemon API as ten tools, so an agent can read state, write state, bind events and push frames.

ds-focus

Publishes the focused window as app/focus/changed. Bindings on that topic recolor keys. The daemon does not need to know about Wayland.

Why it is shaped this way

The Python predecessor ran a 10 ms tick on one thread. That thread polled HID, painted keys, advanced GIFs, polled focus and ran plugin work. A slow HID write blocked the loop. The Tauri predecessor moved the engine into a desktop app, so the app became the control interface and the engine shipped with the UI.

deckstack makes two separations that the earlier designs did not have. The control plane and the frame plane are different sockets with different encodings, so pushing a frame touches no JSON state and bumps no revision. Plugins are separate processes with a manifest, so a slow plugin cannot hold the device writer.

The reference deck

salon-deck is the deck we run. It is 2,487 lines of Python across five modules and their tests, 1,025 of them in one long-lived micro-app. It paints the 15 keys, maps the dial to volume and mute, the rollers to window and workspace scroll, and drives the Salon lights through a HueMux bridge. It contains no HID code and no device protocol constants.

The bindings live in the daemon. Python subscribes to the topics they emit, composes key images, and writes them back through the daemon, which encodes and chunks the JPEG to the panel.

# a binding, written once
ds bind deck/control/keys.0/down --do '{"do":"emit","topic":"app/salon/key/0"}'

# the micro-app listens for the topic
ds watch 'app/salon/key/*' --ndjson

# paint a key through the daemon
ds set /controls/keys/0/image --file key0.png

Two things stay outside the daemon on purpose. The first is the desktop session. KWin provides the screen colour, and ydotool and gdbus handle media and window actions. The second is the HueMux bridge. Neither is deck hardware.

A plugin is the third option. deckstack-lights runs as its own process with one network grant, net:lights.lan, and speaks to the bridge only through the daemon.

Try it

The virtual device speaks the same HID report protocol, so the daemon, the CLI and the virtual device run without hardware.

cargo build --release --workspace
target/release/ds-vdev --socket /tmp/vdev.sock &
target/release/ds daemon start --device virtual:/tmp/vdev.sock
target/release/ds daemon status
target/release/ds set /controls/keys/0/image --json '{"kind":"color","value":"#3cc86e"}'
target/release/ds bind deck/control/keys.0/down --do '{"do":"set","path":"/settings/dim","value":0.2}'
target/release/ds daemon stop

Limits

  • Linux only. The device layer, the focus sender and the udev rules are Linux code.
  • ds stream push is wired in the CLI, but the daemon in this tree does not bind stream.sock yet.
  • emit, events, plugin and token are later-phase CLI verbs and are refused with exit 1. Events and plugin invocation work through bindings and the daemon.
  • There is no web UI and no preset library. The daemon starts from an empty state document.
