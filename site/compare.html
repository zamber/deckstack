What the predecessors got right

The Python project mapped the device and built a vocabulary people used: pages, presets, flows and actions. That vocabulary still shapes what a deck is expected to do.

The Tauri project wrote the protocol and device layers in Rust, and it got native frame throughput. deckstack reuses those crates, mh-protocol and mh-device, pinned by revision. The HID report format was not rewritten.

What changed

One writer

HID ownership moved into ds-device behind the daemon. No client links hidapi. Every screen and LED write goes through one path that checks the safety policy.

Two planes

Control is NDJSON. Frames are DSF1 binary records on a second socket. A frame push updates no durable state and bumps no revision, so queries keep answering while the deck is streaming.

State as a document

State lives at paths with a revision. A write can compare against if_rev. Subscriptions carry the revision that produced each event, so a client can detect a conflict or a gap.

Plugins as processes

A plugin declares its actions and capabilities in a manifest. The host mediates state and network access. A stuck plugin cannot hold the device writer.

Agents as peers

The CLI, the MCP bridge, the focus sender and your scripts speak the same protocol. There is no privileged UI client in the alpha.

Protocol reuse

The device protocol crates come from the upstream Rust project. deckstack adds process boundaries and a state contract around them instead of starting the hardware layer again.

The reference deck

salon-deck is the deck that runs on deckstack. It is 2,487 lines of Python across five modules and their tests. The long-lived part is one process of 1,025 lines.

The Python side holds policy and composition. It contains no HID code and no device constants. The Rust side owns the device and the state. The two meet at the socket.

# a binding, written once through the CLI
sd bind deck/control/keys.0/down --do '{"do":"emit","topic":"app/salon/key/0"}'

# the micro-app subscribes and composes
for event in client.watch("app/salon/key/*"):
    client.set("/controls/keys/0/image", image_for(event))

# the daemon encodes the image and chunks it to the panel

This is the split the earlier designs did not have. The engine that talks to HID is not the process that decides what a key should show, and neither is the process that draws the UI.

deckstack also has 15,405 lines of Python conformance and end-to-end tests. That is where a large part of the verification lives, and it is why the Python number in the table excludes tests.

Limits

  • Linux only. The device layer, the focus sender and the udev rules are Linux code.
  • ds stream push exists, but the daemon does not bind stream.sock in this tree.
  • The emit, events, plugin and token CLI verbs are later-phase and refused with exit 1.
  • Plugin install is a file copy until ds plugin install lands.
  • Hardware checks use a camera check against a specific panel. Another panel revision may need new goldens.
  • There is no web UI and no preset library. The daemon starts from an empty state document.

The design record is in the repository: docs/10-architecture.md, docs/contracts/, docs/discovery/ and the ADRs.
