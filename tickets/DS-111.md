## Context

DS-109 added the atomic panel path: `/controls/panel/image` accepts one 480x272 image
and produces one `02 35` push. On the Salon repaint it cut the median from 0.102 s (15
per-key writes, 30 `ds` processes) to 0.017 s (one panel write).

Clients that only have fifteen colours still cannot use that path without carrying the
panel geometry and a renderer. Their alternatives today are 15 `ds set
/controls/keys/N/image` calls (15 process spawns, 15 transactions, 15 JPEG encodes,
15 `02 36` pushes, rolling shutter) or one `/controls/panel/image` file write with a
client-rendered image. DS-110 exposes the existing multi-op transaction but still
per-key visuals; it does not compose a panel.

The keys windows are fixed by the hardware: 72x72 tiles at x=5,104,203,303,402 and
y=1,101,199 on the 480x272 panel (`docs/contracts/streaming.md` §1,
`upstream/PROTOCOL.md:81`). The daemon already owns panel JPEG encoding
(`frames::encode::encode_solid` and `encode_rgb`).

## Goal

One call carries fifteen `#rrggbb` colours; the daemon stores one panel visual, composes
the 480x272 image, and sends one panel push. No per-key processes, encodes or reports.

## Scope

- **Schema**: add a panel-only `colors` visual, `{"kind":"colors","value":[15 ×
  #rrggbb]}`. Define `$defs/panelVisual` (the existing `visual` OR `colors`) and
  `$defs/panelControl` (`image` -> `panelVisual`, plus `label`/`brightness`); point
  `/controls/panel` at it. Keys and dial keep `screenControl`, so `colors` stays
  panel-only at the schema level.
- **Daemon**: `ImageSource::Colors([ [u8;3]; 15 ])`, parsed in `plan_image_source`;
  `encode_image` routes it to a new `frames::encode::encode_panel_colors`.
- **Encoder**: `encode_panel_colors` builds a 480x272 RGB buffer (background
  `#000000`) and fills each 72x72 key window from the array; then `encode_rgb(Panel,
  …)`. Keep the window table in one named constant with the streaming.md reference.
- **Device cache**: a Panel image and Key images are mutually exclusive in the re-push
  cache. Caching a Panel action drops cached `Image { target: Key(_) }` actions;
  caching a Key image drops a cached Panel action. Without this, a reconnect after a
  bulk colour update can replay stale key tiles over the panel (or a stale panel over a
  newer key).
- **CLI**: `ds colors <json-array>` with exactly 15 strings; it builds the visual and
  sends the same single `set` as `ds set /controls/panel/image --json …`. Human output
  is `ok rev=N`, `--json` the usual one-object envelope. Wrong arity/JSON/hex exits 1
  before contacting the daemon. Document the verb in `docs/contracts/cli.md` §4 and the
  help text.
- **Bench**: `tests/bench/colors.py` boots ds-vdev + ds-daemon, warms both paths, runs
  5 alternating pairs (A = one colours call, B = 15 per-key sets), counts errors, and
  reports median/range plus load average and `nproc`. It also records the vdev frame
  targets to prove A pushes one panel and B pushes keys.

## Out of scope

- Sparse/partial colour updates: the panel is one value; mixed visuals (labels, icons,
  files) still go through the rendered `/controls/panel/image` file path (DS-109).
- Rewriting `/controls/keys/N/image` from a colours call. This is a panel display
  update with the same semantics as DS-109, not a per-key state write.
- `set-batch` and generic multi-path writes (DS-110), image batching, animation.
- Client-side renderers (Salon app) and a new IPC op.

## Implementation notes

Read first: DS-109, `docs/contracts/streaming.md` §1, `docs/contracts/state.md` §3,
`crates/ds-daemon/src/device.rs` (`plan_push`, `plan_image_source`, `encode_image`),
`crates/ds-daemon/src/frames/encode.rs`, `crates/ds-daemon/src/ipc.rs` (`op_set`),
`bins/ds/src/cli.rs` (verb parsing and help).

**Shape chosen.** A `colors` visual on the existing panel path. The alternative (a new
`set-colors` IPC op that expands to 15 per-key image ops) needs a transaction-boundary
hook in the state→device forwarder to collapse 15 events into one push and leaves the
panel value and the per-key values disagreeing about what is displayed. The panel path
gives each piece of state one owner (the panel image), one way to send it (`set` → state
→ device), and asks the caller only for fifteen colours.

**Why panel-only.** A 15-colour array is meaningless for one key or the dial. Do not add
`colors` to the shared `visual` definition: a schema that accepts it on any screen
forces the daemon to reject a committed value. `panelVisual`/`panelControl` keeps the
rejection before the transaction.

**Composition.** Do not decode JPEG in tests. Factor the pixel fill into a small pure
function (or expose the RGB buffer) and assert exact pixels at every tile centre, one
edge pixel and one gap pixel; then assert the frame is one `0x35` push. JPEG q80 is
lossy, so decoded-pixel equality is the wrong oracle.

**CLI parsing.** The global `--json` is the output mode, not the value flag; the array
is the one positional argument, exactly like `ds set`'s inline value. `ds colors
'["#101010", …]' --json` prints the one-object envelope. Reject 14/16 entries and any
value outside `^#[0-9a-fA-F]{6}$` with exit 1. Register the verb in the help walk and
coverage table in `tests/conformance/cli/run.py` (cases 010/020 fail until you do).

**Benchmark.** Run both sides on the same debug binaries the conformance harness uses
(`cargo build --bin ds --bin ds-daemon --bin ds-vdev --bin ds-vdevctl`); the limiter is
process spawn plus the vdev write, not CPU, so interleave A/B and report the load
context. One colours call should be close to one panel-file write; if it is not, find
the limiter before reporting. Count non-zero exits and verify the state after each run
(question 7 of the benchmark checklist).

## Acceptance

- `ds colors '["#ff0000", … 15]'` returns one rev; `ds set /controls/panel/image
  --json '{"kind":"colors","value":[…] }'` accepts the same value.
- The composed RGB buffer is 480x272; tile N is exactly the requested colour at its
  centre and the gap pixels are `#000000`.
- One `0x35` frame appears in `ds-vdevctl frames panel`; `frames key:N` does not grow.
- 14/16 entries, bad hex, or `colors` on `/controls/keys/0/image` -> `E_SCHEMA`, exit 1,
  and the state rev does not move.
- `tests/bench/colors.py`: 5 alternating runs per side, 0 errors, medians and ranges
  reported; colours ≤2x one panel-file write and ≥3x faster than 15 per-key writes.
- The re-push cache test: a panel image drops cached key images and a key image drops a
  cached panel image.

## Risks

- **Tile geometry off by one** leaves stripes or clipped tiles. Pin all 15 centres plus
  the 72x72 edges in the pure composer test.
- **JPEG is lossy.** Test the RGB buffer exactly and the device frame count, not decoded
  colour equality; keep a tolerant probe only if the end-to-end test needs one.
- **Contract change.** `schemas/state.json`, `state.md` and the fixture gate are
  normative; run `sh tests/fixtures/validate.sh` and add a negative fixture for
  `colors` on a key.
- **Help-walk conformance** fails the moment `ds colors --help` exits 0 without a walk
  entry; update 010/020 in the same commit.
- **Cache invalidation** changes reconnect behaviour; keep it scoped to image actions
  and cover both directions with a unit test.
