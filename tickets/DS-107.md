## Context

The HID transport sent feature reports through `hid_write`, so software mode never engaged
(52b4803). The committed `panel.jpg` and `key0.jpg` goldens show the blue boot animation, not
the intended black/white states, so the "3/3 pass" compared the broken state to itself. Two
other gaps surfaced: `plan_push` has a panel-image branch for `/controls/keys/image` but the
state write path rejects it (`control index 'image' out of range`), and the app's roller LED
writes log `push /controls/rollers/0/led failed: no led report`.

## Goal

The verification fixtures and the documented control paths match what the hardware actually
does.

## Scope

- Re-record the camera goldens with the deck in the intended states; keep the calibration.
- Decide whether `/controls/keys/image` (panel) is a supported write path; expose it or remove
  the dead `plan_push` branch and document the per-key route.
- Pin roller LED support or document why the M0 rollers reject the LED report.

## Out of scope

New effects and the base ring (DS-105).

## Implementation notes

The camera is `/dev/video2`, 1280x720 MJPEG. The goldens' `capture_command` and manifest are in
`tools/verify/golden/`. The panel path error comes from `crates/ds-state/src/path.rs`; the plan
branch is in `crates/ds-daemon/src/device.rs`.

## Files and boundaries

Only the four `touches`. Protected: `BRIEF.md` R1-R12, `docs/discovery/`, `docs/reviews/`.

## Acceptance

- Goldens fail on the old boot-animation state and pass on the re-recorded intent.
- Panel path has one documented behaviour, not a dead branch.
- Roller LED behaviour is explicit.

## Verification

`python3 tools/verify/golden/run_golden.py --only key0,panel,led`;
`python3 tools/report-issue` bundle attached.

## Risks

Camera aim/lighting drift can invalidate a re-record; use the calibration overlay and the
`panel_hint` from the manifest.

## Definition of done

The verification suite is a real oracle again and the control vocabulary matches runtime.
