## Context

Hardware gets unplugged. The roadmap phase-2 exit requires replug ≤ 5 s
(docs/60-roadmap.md, upstream PROTOCOL.md:172-177 reference). The daemon's device task
must rescan, reconnect, re-push current state, and handle a device that stops
answering.

## Goal

Resilient device task: hot-plug rescan/reconnect/re-push and unresponsive-device
detection with bounded recovery.

## Scope

- `crates/ds-device/src/hotplug.rs`: udev-event or poll-based rescan on the hid
  transport; reconnect with re-handshake (DS-022 path).
- `crates/ds-daemon/src/device_task.rs`: on reconnect, re-push full current state
  (images/colors) to the device; watchdog on report liveness (≤ 100 ms liveness check
  per roadmap); unresponsive → mark device down, keep serving IPC, retry with backoff.
- Fault-injection unit tests (mock transport that stops answering / disappears).
- Hardware smoke replug case.

## Out of scope

Guard/handback on daemon exit (DS-024), camera verification (DS-027/028).

## Implementation notes

Read docs/components/daemon.md (device task) and device-driver.md. Never block IPC on
the device: the device task is a separate task with bounded channels (DS-015 design).
Replug budget ≤ 5 s end to end.

## Files and boundaries

Only `touches`. Coordinating with DS-015's `crates/ds-daemon/` is fine (sequenced, not
simultaneous).

## Acceptance

Fault-injection tests green; on real hardware, replug ≤ 5 s with state re-pushed
(verified by one frame per target after replug).

## Verification

`DS_HARDWARE=1 python tests/hw/smoke.py`; unit tests; check.sh; board validate.

## Risks

USB enumeration races — poll with backoff rather than event-only.

## Definition of done

PR merged; replug ≤ 5 s demonstrated; unresponsive handling tested.
