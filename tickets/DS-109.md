## Context

The Salon app repainted a layer by writing 15 per-key images, each through its own `ds`
process and its own device transfer. The visible result was a rolling shutter and a median
0.102 s update for the per-key path after the favourites cache was warm; 30 `ds` processes.
The device already supports a whole-panel image (480x272) and `plan_push` had a dead
`/controls/keys/image` branch, but the state path rejected it.

## Goal

A client can send one whole-panel image and the keys module repaints atomically.

## Scope

- Add `controls.panel` to `schemas/state.json` as a `screenControl`.
- Allow `/controls/panel/...` in the write-path vocabulary.
- Map `/controls/panel/image` to `ImageTarget::Panel`.
- Pin the path with tests.

## Out of scope

Batch state transactions (DS-110) and the client renderer (Salon app).

## Implementation notes

The panel is the 480x272 keys screen; key tiles sit at x=5,104,203,303,402 and y=1,101,199.
The per-key path remains for compatibility. The client composes the panel from its 15 tiles
and writes the leaf image; one transaction, one device push.

## Files and boundaries

Only the three `touches`. Protected: `BRIEF.md` R1-R12, `docs/discovery/`, `docs/reviews/`.

## Acceptance

- `/controls/panel/image` is accepted and produces one `pushed Image { target: Panel }`.
- Existing per-key path and tests still pass.

## Verification

`cargo test -p ds-daemon --lib` (199), `cargo test -p ds-state --lib` (28);
`ds set /controls/panel/image --file /tmp/panel-speed.png` → `pushed Image { target: Panel }`;
Salon benchmark: per-key median 0.102 s, panel median 0.017 s, 5 alternating runs, 0 errors.

## Risks

The panel must be exactly 480x272; a wrong-sized frame is refused. The per-key path stays
available, so mixed clients can still use it.

## Definition of done

A client can repaint all 15 keys with one write and no rolling shutter.
