## Context

With the udev ACL fixed and the vendor app stopped, `ds-daemon --device hid:` reaches the deck
but every send fails with `module keys virtual-01fe is not connected`. The device path passes
`virtual_module_id(kind)` (serial `virtual-01fe`) to the real hid transport, which only knows
the enumerated ids (`serial MHKD15...`). The vdev path hides this because virtual ids are its
real ids.

## Goal

The transport owns module identity: the daemon asks its transport for the id of a module kind,
so `hid:` sends to the enumerated modules and `virtual:` keeps exactly today's behaviour.

## Scope

- Add module resolution to the `Transport` trait (`fn module_id(&self, kind) -> Option<ModuleId>`
  or `fn modules(&self) -> Vec<ModuleId>` plus a lookup), implemented by `VirtualTransport`
  (virtual ids) and the hid transport (enumerated ids from its map/`enumerate`).
- Replace `virtual_module_id(kind)` on the send paths: `device.rs` `send_action` (LED and image),
  `frames/writer.rs`, `frames/service.rs`, `frames/animate.rs`, `guard.rs`; hotplug comparison in
  `device_task.rs` must use the real ids.
- No change to the state document, contracts, or vdev behaviour.
- Unit tests: both transports resolve keys/panel/dial/knobs/rollers to their own ids; unknown
  kind is an error, not a panic.

## Out of scope

Changing the report codec, the handshake sequence, or hotplug policy.

## Implementation notes

Read `crates/ds-device/src/{transport,vtransport,hid/mod,module}.rs` and the call sites above.
Prefer a small `ModuleRegistry`/closure threaded through the send path over a global. Keep the
transport trait object-safe.

## Files and boundaries

Only the paths in `touches`.
