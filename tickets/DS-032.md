## Context

Phase 3 producer surface. docs/contracts/cli.md §1 defines the `stream` group
(`push`/`stats`/`stop`); docs/contracts/ipc.md §1.2 fixes the transports: `push` is
control `stream-open` + DSF1 binary on stream.sock, `stats`/`stop` are NDJSON ops.
docs/contracts/streaming.md §7 gives the producer examples incl. directory mode and
external ffmpeg decode. The CLI skeleton and output/exit-code contract are DS-016.

## Goal

The `ds stream` verb group working end to end against the DS-031 frame service on
ds-vdev, conforming to cli.md and ipc.md.

## Scope

- `bins/ds/src/stream/`: `push` (single file; `--dir` + `--fps` + `--loop` animation,
  frames read in order, ≤ 300 frames @ ≤ 30 fps enforced client-side with a clear
  error), `stats`, `stop`. Target parsing/validation (`keys|key:<0-14>|dial`).
- Transport: `stream-open {target, credits}` on the control socket, then DSF1 frames
  on stream.sock with `DSctl`-prefixed acks; handle `stream-nack`/`E_LIMIT` as
  backpressure (exit 5), never spin.
- Output: human one-line-per-fact; `--json` one object; errors actionable with exit
  codes per cli.md §3/§5.
- `docs/contracts/cli.md`: only if a clarification is strictly needed — the stream
  grammar is already normative there; prefer conforming.

## Out of scope

The daemon-side service (DS-031), encoder (DS-030), bench (DS-033), GIF decode pipeline
(DS-034 — the CLI passes GIF frames through, the daemon decodes), vdev throttle
(DS-035), WS/HTTP adapter (DS-074).

## Implementation notes

Read docs/contracts/cli.md, docs/contracts/ipc.md §1.2/§2, docs/contracts/streaming.md
§7, docs/components/cli.md. Reuse ds-client (DS-012/DS-015) for the control op and a
raw stream-socket writer for DSF1; keep the CLI stateless. Directory mode: read
`%04d`-style sorted filenames, send meta `{target, seq, ts_ms, format, w, h, frames,
fps, loop, crc32}` per schemas/stream-frame.json.
