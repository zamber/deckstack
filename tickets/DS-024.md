## Context

The daemon owns the hardware while running; on exit it must leave the deck in a safe,
known state (roadmap phase-2 exit: SIGTERM handback). Invariants: never backlight-0 the
dial; forbidden HID commands unrepresentable — handback must use safe builders only.

## Goal

A guard module in ds-daemon that on clean exit (SIGTERM/normal) performs handback, and
on crash leaves enough on disk (state file + token) that the next start recovers.

## Scope

- `crates/ds-daemon/src/guard.rs`: signal handler / drop-guard performing handback
  sequence (via ds-protocol safe builders): finish or abort in-flight frame pushes
  atomically, set backlight per policy (never 0), release device cleanly.
- Crash recovery: persist state atomically (DS-011 already does); on start, if a stale
  lock/token exists from a crashed run, take over cleanly (re-handshake, re-push).
- Unit tests with a mock transport recording the handback command sequence.
- Hardware smoke SIGTERM case.

## Out of scope

Hot-plug (DS-023), udev (DS-025), camera checks (DS-027/028).

## Implementation notes

Read docs/components/daemon.md and AGENTS.md invariants. Handback must be idempotent
and bounded in time (do not hang shutdown; watchdog force-exits after N ms with a
log line).

## Files and boundaries

Only `touches`: `crates/ds-daemon/src/guard.rs`, `tests/hw/`.

## Acceptance

SIGTERM → handback sequence observed on hardware (safe state), exit 0; kill -9 →
next start recovers and re-pushes.

## Verification

Hardware smoke; unit tests; check.sh; board validate.

## Risks

Shutdown hangs — enforce a hard timeout on the guard.

## Definition of done

PR merged; handback + crash recovery proven; invariants intact.
