## Context

Phase 4 storage + CLI for bindings. S2: `/bindings` is an ARRAY because topics contain
'/' (schemas/state.json §bindings, docs/contracts/state.md §2). Contract:
schemas/binding.json (normative — change schema and docs/contracts/actions.md in the
same commit), cli.md §1 (`bind`/`unbind` verbs). Empty-state invariant: fresh start
has empty `/bindings` (asserted by DS-018).

## Goal

Users and agents can create, list, inspect, and delete bindings through the CLI and
API, with schema validation and stable ids.

## Scope

- `crates/ds-state/src/bindings.rs`: array CRUD inside the state document, id
  assignment (`b%04d`), uniqueness, transactional add/remove (rev bumps — bindings
  ARE durable state, unlike frames).
- `bins/ds/src/bind.rs`, `unbind.rs`: verb implementations per cli.md §1/§4 examples
  (`ds bind deck/control/keys.0/down --do 'plugin demo.bump {\"by\":1}' --json` →
  `{"id":"b0001"}`); step strings parsed as JSON and schema-validated client-side for
  fast errors, re-validated daemon-side.
- `schemas/binding.json`: only if validation gaps are found (e.g. `when` operators
  list); keep the no-code-field invariant (T2).
- Conformance under `tests/conformance/bindings/`.

## Out of scope

Step execution/vocabulary (DS-042), exec policy (DS-043), router dispatch (DS-040),
focus ingest (DS-044), plugin steps' runtime (phase 5) — `bind` stores them, validation
of the step shape only.

## Implementation notes

Read schemas/binding.json, docs/contracts/actions.md §2, docs/contracts/state.md §2,
cli.md §1/§4. `when` conditions reference `path` (state) or `payload` (event field) —
store verbatim; evaluation is DS-042. Keep `--do` parsing strict: malformed JSON →
exit 1 with the schema error shape from cli.md §5.

## Files and boundaries

Only `touches`: `schemas/binding.json`, the ds-state bindings module, the two new CLI
verb files, `new:tests/conformance/bindings/`. Do not edit `crates/ds-daemon/src/router/`
(DS-040/042/044) or other `bins/ds/src/` verb files.

## Acceptance

Conformance bindings cases green on vdev: bind → id printed; get /bindings lists it;
watch streams the add; unbind removes; negative schema cases (code-ish step, bad
topic) exit 1; unknown id unbind exits 2.

## Verification

cargo tests, conformance -k bindings, fixture gate (validate.sh covers binding.json),
workspace tests, check.sh, board validate — see metadata.

## Risks

Id collisions after unbind/re-add — ids are monotonic per daemon run, never reused
within a data dir. Schema drift between client-side parse and daemon validation — test
both paths with the same corpus.

## Definition of done

PR merged; bindings CRUD green end to end; DS-042 can execute what DS-041 stores.
