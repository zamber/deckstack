## Context

The mh-protocol safety rules are invariants (AGENTS.md): forbidden HID commands stay
unrepresentable; never backlight-0 the dial; software-mode handshake before reads.
docs/20-security.md is the threat model; these rules need machine-checked conformance,
not just docs.

## Goal

A safety conformance suite that proves the forbidden-command, handshake-order,
backlight, and no-raw-escape invariants on both vdev (CI) and hardware.

## Scope

- `tests/conformance/safety/`: cases asserting (a) forbidden command set cannot be
  constructed via ds-protocol and is rejected with `E_DEVICE` + zero bytes on the wire;
  (b) no device reads before software-mode handshake; (c) backlight 0 never emitted;
  (d) no raw/escape verb exists in the CLI or IPC surface (grep-level + API-level
  checks).
- Wire-level checks: capture traffic on the vdev socket and assert no forbidden opcodes
  ever appear.
- Hardware: the forbidden-command step of `DS_HARDWARE=1 python tests/hw/smoke.py`.

## Out of scope

The broader security conformance mapping T1-T12 (DS-081, later phase), exec policy
(DS-043, phase 4).

## Implementation notes

Read docs/20-security.md, AGENTS.md invariants, and the ds-protocol safety tests
(DS-010). Safety cases must fail loudly if a rule becomes representable — that is the
point.

## Files and boundaries

Only `touches`: `tests/conformance/safety/`, `docs/20-security.md` (only if a mapping
needs writing; prefer conforming).

## Acceptance

All safety cases green on vdev; forbidden → `E_DEVICE` + zero bytes verified on
hardware smoke; a deliberately unsafe builder attempt fails the suite.

## Verification
