## Context

mh-protocol safety invariants (AGENTS.md): software-mode handshake before reads; never
backlight-0 the dial; forbidden HID commands unrepresentable. On real hardware the
daemon must complete the software-mode handshake and module init before issuing reads
or writes.

## Goal

The real-device bring-up path: handshake → module init → safe operation, with every
write via ds-protocol builders.

## Scope

- `crates/ds-device/src/handshake.rs`: software-mode handshake state machine over the
  hid transport; block reads until handshake completes; module init (per-module config
  push) after handshake.
- All device writes route through ds-protocol safe builders (DS-010); add tests that
  the daemon init path cannot be constructed without the handshake state.
- Hardware smoke: handshake + init + one frame per target green on the real deck.

## Out of scope

Hot-plug rescan (DS-023), guard/handback (DS-024), camera verification (DS-027/028).

## Implementation notes

Read docs/components/device-driver.md and the upstream protocol notes referenced from
it (replug ≤ 5 s expectations are DS-023). Type-state the handshake so "read before
handshake" is a compile error where possible.

## Files and boundaries

Only `touches`: `crates/ds-device/src/handshake.rs`, `tests/hw/`.

## Acceptance

`DS_HARDWARE=1` smoke: enumerate → handshake → init → one frame per target, all green;
no reads before handshake (asserted in tests).

## Verification

Hardware smoke output in PR record; unit tests in CI; check.sh; board validate.

## Risks

Handshake timeouts on flaky USB — bounded retries, then a clear error (feeds DS-023's
unresponsive handling).

## Definition of done

PR merged; handshake/init proven on hardware; safety invariants still machine-checked.
