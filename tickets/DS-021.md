## Context

Phase 2 brings up real hardware on Linux (docs/60-roadmap.md). DS-014 defined the
transport trait with a virtual impl; this ticket adds the real HID transport
(hidraw/libusb) implementing the same trait, so the daemon is transport-agnostic.

## Goal

`hid:` transport in ds-device: enumerate MasterHub modules, open, reader threads
pushing reports into the daemon's device task.

## Scope

- `crates/ds-device/src/hid/`: hidraw backend (preferred; libusb fallback per
  docs/components/device-driver.md), enumeration (VID/PID per mh-protocol), open by
  path or first-found, reader thread(s) → report stream.
- Same `Transport` trait as virtual; device URI `hid:` / `hid:<path>`.
- Hardware-gated tests under `tests/hw/` that skip cleanly when no deck is attached
  (`DS_HARDWARE=1` enables them).
- Permissions note: without udev rules (DS-025) opening may need root — tests must
  detect and SKIP with a clear message, not fail.

## Out of scope

Handshake/safe builders (DS-022), hot-plug (DS-023), guard (DS-024), udev rules
(DS-025).

## Implementation notes

Read docs/components/device-driver.md and ADR-010 (mh-device reuse). Keep all unsafe
HID writes behind the ds-protocol safe builders (DS-010). If hardware differs from
vdev behaviour, fix the virtual model first (escalation rule).

## Files and boundaries

Only `touches`: `crates/ds-device/src/hid/`, `tests/hw/`.

## Acceptance

On a machine with the deck attached, the hid transport enumerates and opens it and
reports arrive; unit tests green without hardware.

## Verification

Unit tests (no HW) in CI; `DS_HARDWARE=1` smoke enumerate step on hardware; check.sh;
board validate.

## Risks

hidraw vs libusb differences across kernels — pick hidraw, keep libusb as fallback
behind a feature flag if needed.

## Definition of done

PR merged; enumeration+open+reports proven on the real deck; CI still hardware-free.

## Notes

DS-022 (handshake) builds directly on this.
