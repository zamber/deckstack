## Context

docs/90-verification.md requires golden camera checks for representative targets —
key:0, the panel, LED states — plus a repeatable calibration procedure, so pixel claims
are verified, not assumed (ADR-015).

## Goal

Golden capture set + calibration procedure + check wiring so `deckstack-verify check`
compares live hardware pixels against goldens.

## Scope

- `tools/verify/golden/`: golden images/masks for key:0, panel, LED states; a
  `CALIBRATION.md` (or section in docs/90-verification.md) describing the calibration
  procedure (camera position, lighting, region mapping, tolerance) and how to
  regenerate goldens deliberately.
- Wire `deckstack-verify check <target>` to compare against the right golden with the
  documented tolerance; fail with diff artifacts on mismatch.
- Guard the empty-state invariant: goldens live under tools/verify/golden/, never in
  any default state.

## Out of scope

The harness itself (DS-027), more targets (add as needed later), CI camera jobs
(CI stays vdev-only).

## Implementation notes

Read docs/90-verification.md. Goldens must be reproducible: record camera, lens,
distance, and calibration params with each golden.

## Files and boundaries

Only `touches`.

## Acceptance

On the real deck: `deckstack-verify check key:0`, `check panel`, LED check all pass
against goldens; a deliberately wrong state fails with a useful diff.

## Verification

Hardware check output in PR record; check.sh; board validate.

## Risks

Lighting drift invalidates goldens — the calibration procedure must include a
re-calibration trigger.

## Definition of done

PR merged; goldens + calibration committed; camera checks green on hardware.

## Notes

Completes the phase-2 camera-verification exit criterion together with DS-027.
