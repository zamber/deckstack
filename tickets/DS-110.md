## Context

The Salon panel path (DS-109) removes the 15 image writes, but clients still make several
independent `ds` calls for labels, brightness and LED state. Each call is a process spawn and
a transaction. The IPC `set` op already accepts an `ops` array; the CLI only exposes one set.

## Goal

A client can submit a multi-path state update in one round trip and one transaction.

## Scope

- Add a `set-batch`/`apply` CLI verb with a JSON spec (`[{path,value}, ...]`).
- Validate every path and value before committing; one rev; clear error on any invalid entry.
- Document the grammar and exit codes.

## Out of scope

The atomic panel image path (DS-109) and image batching; the panel is the fast display route.

## Implementation notes

The daemon `set` op with `ops` is the existing transaction; the CLI must not loop over
`set` calls. Keep the output one line with the resulting rev. Reuse the existing schema
validation and exit-code mapping.

## Files and boundaries

Only the three `touches`. Protected: `BRIEF.md` R1-R12, `docs/discovery/`, `docs/reviews/`.

## Acceptance

- A 3-path batch produces one rev and all three values are visible.
- An invalid path fails before any value is written.

## Verification

`cargo test -p ds-cli`; `ds set-batch --file /tmp/batch.json`; `python3 tools/tickets.py validate`.

## Risks

Partial writes are worse than slow writes; validate the whole batch before the transaction.

## Definition of done

A client can set labels, brightness and LEDs in one call; the panel remains the icon fast path.
