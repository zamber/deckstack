## Context

DS-020's e2e walking skeleton exposed the gap: `crates/ds-daemon/src/device.rs` `plan_push`
maps only colour/LED visuals and logs `kind: file` as "out of scope for DS-015, ignored".
`ds-vdev` only stores frames reassembled from 0x35/0x36/0x45 image-chunk reports, so
`ds-vdevctl frames key:0` has nothing to report after a file set.

## Goal

The daemon's device task pushes every displayable visual (key/panel/dial images) to the
device as chunked image reports, so the walking skeleton and phase 2 have one code path.

## Scope

- Extend the state->device mapping for `image` visuals on keys, the panel and the dial:
  `kind:file` reads the file (respecting /policy/fs/roots and the file size limit) and
  pushes its bytes; `kind:color` encodes a solid image (a minimal PNG or the documented
  phase-1 placeholder) and pushes that.
- Use the ds-device chunking/report builders (0x35 keys / 0x36 key:N / 0x45 dial) and the
  rate limit; do not invent a second chunker.
- Keep the image bytes off the state lock and out of the state document (S1).
- Tests: extend crates/ds-daemon/tests/daemon.rs so a file set against ds-vdev produces a
  frame whose sha matches the file, and a colour set produces a frame.
- Document the phase-1 caveat in docs/components/daemon.md: the file bytes are sent
  unchanged; JPEG baseline 4:4:4 re-encode is DS-030 (phase 3).

## Out of scope

JPEG re-encode and animation (DS-030/DS-034), latest-frame-wins queues and writer threads
(DS-031), real HID (DS-021), GUI/LED effects beyond what the mapping already does.

## Implementation notes

Read `crates/ds-daemon/src/device.rs` `plan_push`/push loop, `crates/ds-device/src/{chunks,report,frame}.rs`, `crates/ds-vdev/src/hub.rs` (what it reassembles), the sheet
limit in `docs/contracts/streaming.md`, and `schemas/state.json` `$defs/visual`. Keep the
device task bounded and non-blocking for IPC.

## Files and boundaries

Only `crates/ds-daemon/src/device.rs`, `crates/ds-daemon/tests/daemon.rs`,
`docs/components/daemon.md`. If a ds-device API gap blocks the push, report it.

## Acceptance

`python tests/e2e/run.py` is fully green, including step 3's sha comparison.

## Verification

`cargo test -p ds-daemon`; `python tests/e2e/run.py`; `sh tools/check.sh`; board validate.

## Risks

Sending raw PNG bytes to a device that expects JPEG is a phase-1 liberty; keep it in the
documented caveat and let DS-030 own the real encoding. Do not let a push failure stall the
state task.
