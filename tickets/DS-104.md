## Context

Reproduced 2026-11-24 against the 0.1.0 release with a private vdev+daemon: setting
`/controls/keys/0/image` to `{"kind":"color","value":"#3cc86e"}` makes `ds-vdevctl frames`
list `key:0 … 771B seq=5`; setting `/controls/keys/1/image` to
`{"kind":"text","value":"CPU 2%","fg":"#ffffff","bg":"#000000"}` records module writes
(`pid=0x01fe kind=0x01 len=320`) but `frames` lists no `key:1`, and
`ds-vdevctl frames key:1` exits 1 with `no frame for target 'key:1' yet`.

`docs/components/virtual-device.md` does not say which visual kinds are reassembled, and
`agents.md` §5's static-image guidance implies `set` renders any visual. A micro-app author
verifying text output on vdev gets a false negative. This came out of the fresh-agent
exercise (Vibe run `run-4004503968-63723`).

## Goal

The vdev's frame surface is pinned and documented: either text visuals are reassembled like
colours (with a test), or the limitation is stated exactly where authors look.

## Scope

- Investigate `crates/ds-vdev` frame reassembly and the report encoding for text vs colour
  visuals. Determine whether this is a vdev reassembler gap or the daemon genuinely sends a
  different report for text that the vdev does not model.
- If it is a vdev gap and phase-1 intent covers text: extend reassembly and add a test that
  sets a text image and asserts `frames` contains the target (hash/size/seq as for colour).
- If text frames are out of phase-1 scope: document it in
  `docs/components/virtual-device.md` (frame matrix: visual kind → frame? / writes only) and
  in the `ds-vdevctl frames` help, including the `<target>` exit-1 case.
- If the cause is the daemon/frame service rather than the vdev, split that into its own
  ticket and land only the documentation here.

## Out of scope

Real-device rendering and the DS-028 camera goldens. Stream/frame-service behaviour changes
unless the investigation proves they are the cause (then split).

## Implementation notes

Start from the reproduction above; `ds-vdevctl writes` shows the raw module reports, `frames`
shows the reassembled targets. Read `docs/components/virtual-device.md`,
`docs/contracts/streaming.md`, and the vdev frame code. Keep the test hermetic (own socket and
data dir under a temp dir).
