### e2e step 3 change (DS-030 deliverable, documented here per the ticket)

`tests/e2e/run.py` step 3 used to assert `ds-vdevctl frames key:0` == sha256(examples/key.png)
because the phase-1 push path forwarded the file bytes unchanged. From DS-030 on, the daemon
re-encodes the image to the device wire format (baseline JPEG, standard Huffman tables,
4:4:4, q90 for key:N — `docs/contracts/streaming.md` §2) before chunking, so the reassembled
vdev frame IS the encoded JPEG. Step 3 now compares against the golden ENCODED-frame sha
`tests/golden/example-key0.sha256` (= sha256 of `encode_frame(key:0, examples/key.png)`,
produced by the pinned `jpeg-encoder =0.6.1`); the byte-count assert became `nbytes > 0`
(the frame is no longer the source file's size). Steps 1/2/4/5/6 are unchanged. Observed:
`python3 tests/e2e/run.py` -> `RESULT: OK` (all 6 steps PASS, bench p99 9.083 ms <= 10 ms),
step 3 line: `PASS 3 ds-vdevctl frames key:0 == golden encoded-frame sha (tests/golden/example-key0.sha256)`.

### Implementation notes

- Encoder crate choice: `jpeg-encoder` pinned `=0.6.1` (small pure-Rust baseline encoder
  with explicit standard-Huffman / 4:4:4 control; no JPEG crate was in Cargo.lock before).
  Wire decoders: `png 0.18`, `zune-jpeg 0.5`, `gif 0.14` (first frame). Recorded in
  `tests/golden/README.md`. `jpeg-encoder`'s `simd` feature is not enabled, so the output
  bytes are identical in debug and release builds — the golden unit test (debug) and the
  e2e (release binaries) assert the same sha.
- `frames::encode::EncodeError` is the typed error; every variant maps to `E_FORMAT`
  (`code()`). Progressive (SOF2+) and optimized-Huffman (non-Annex-K DHT) JPEG inputs are
  rejected structurally before decoding; unsupported containers and over-cap payloads are
  rejected too. The device push path turns these into a logged, dropped push — nothing is
  forwarded (covered by `non_image_file_push_is_refused_with_e_format_and_no_frame`).
- `frames::chunk` builds the raw 320 B reports (`02 <cmd> <chunk u16 LE> <len u16 LE>
  <index> <last> <≤312 B>`); a unit test proves they are byte-identical to the sendable
  `ds_protocol` reports once padded, and a round-trip through ds-vdev's `Reassembler`
  proves reassembly. The send path uses the `ds_protocol` builders (the transport only
  accepts builder-made `Report`s) via `frames::chunk::reports`.
- Touches were extended via `tools/tickets.py add-touch` for `crates/ds-daemon/src/device.rs`
  (push-path wiring), `new:crates/ds-daemon/src/frames/mod.rs` and
  `crates/ds-daemon/tests/daemon.rs` (its phase-1 raw-bytes/PNG-placeholder frame
  assertions now expect the encoded-frame shas). `schemas/stream-frame.json` and
  `docs/contracts/streaming.md` needed no change.
- Golden fixtures: `tests/golden/input.png` (fixed deterministic 72x72 image) ->
  `key0.jpg` / `key0.sha256` / `key0.chunks.bin`, plus `example-key0.sha256` for the e2e
  input. Regenerate deliberately with `DS_GOLDEN_REGEN=1 cargo test -p ds-daemon frames::golden`.
